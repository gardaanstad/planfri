# Planfri

A shared project reference and discussion space for infrastructure and the built environment in Norway — transport, energy, water, public buildings, housing and urban development — built with Next.js 16, React 19, TypeScript, Leaflet, Better Auth, and Drizzle. The interface is in Norwegian Bokmål.

## Run

```sh
bun install --frozen-lockfile
bun run setup
# Add Google OAuth credentials to .env.local, then start:
bun dev
```

Open http://localhost:3000. Working in several worktrees? Run `bun run hub` in a terminal of your own, then `bun scripts/preview.ts` (T3's Preview button) in a worktree serves it on localhost:3000 through the hub, keeping each worktree's dev server running so switching back is instant; open tabs follow the latest switch. A worktree's first `bun dev` or Preview copies the Turbopack dev cache from the checkout that ran most recently (`scripts/seed-dev-cache.ts`), so its first page compiles in seconds instead of half a minute. See [Google OAuth and production setup](docs/google-auth.md) for the Client ID, Client Secret, callback URLs, and Turso configuration.

Deployment: see [Deploy to Vercel](docs/google-auth.md#deploy-to-vercel). Validation: `bun run lint`, `bun run typecheck`, and `bun run test` (Playwright/Chromium).

## Included

- Interactive map with clickable project polygons and road / railway alignments, status colors, zoom, and map layers. Below street zoom every project is also drawn as a dot, and nearby projects group into numbered clusters.
- The map is the place filter: the list and its result count hold the projects inside the current map view (on mobile, the part above the half-height drawer). The first visit opens on all of Norway; later visits reopen on the last area viewed. The count sits on its own line under the list's tabs, in words: “N prosjekter”, or, when matching projects lie outside the view, “N på kartet · P i [sted]”, where pressing the place shows the rest of the place's projects below the list. “Velg sted” names the place in view, or “Hele Norge” when every match is in sight. A first visit finds a welcome at the top of the list, laid out like a project row in the accent's soft wash, until its ✕ closes it for good in that browser.
- Desktop shows the results list and the map side by side. Hovering a card highlights its shape on the map. The divider between them resizes the list (drag, arrow keys, Home/End; double-click resets); the width is remembered in the browser and kept within the window. The list's header holds the logo, the account (or “Logg inn”) and the control that collapses the list.
- Search, category, status and sorting. Both layouts put the tabs, the filters and the place on one line, and the count, sort and view on the next. On desktop the search is a button between the tabs and the filter button that opens a field over the right 60% of the tabs’ line (Escape, its ✕ or a press outside closes it); on phones it sits at the top of the filter sheet, behind one search-and-filter button, and Enter closes the sheet onto the hits (or opens the one hit). A search lists every hit wherever it is, counted as “N treff”, and once the typing pauses the map frames the hits, or the place when the search is a place's name. Category and status sit behind the filter button, both counting what is in view; every status shows until filtered. As soon as a search, category or status differs from the default, “Nullstill filtre” appears on the count's line (desktop) or by the filter sheet's title (phones). An empty map area offers a filter reset.
- Filters, sorting and the map position live in the query string (`q`, `status`, `kategori`, `sorter`, `kart=lat,lng,zoom`), updated with `replaceState` once the map has rested, so a view can be shared and survives a reload. Project URLs keep the same query string.
- Categories are main categories with subcategories (`categoryTree` in `app/lib/categories.ts`): Samferdsel (Vei, Jernbane, T-bane, Sporvei, Kollektiv, Sykkel og gange, Havn, Luftfart), Byutvikling (Bolig, Næring, Byrom og park, Skole, Helse, Kultur og idrett, Forvaltning) and Annen infrastruktur (Kraftproduksjon, Strømnett, Fjernvarme, CO₂-lagring, Drikkevann, Avløp, Overvann), each with an icon (`app/components/category-icon.tsx`; a category without one takes its main's). A project has one or more main categories, each optionally narrowed to subcategories; it reads as its subcategories, or the main when it has none. The filter and the project editors share one menu (`categoryOptions`): main categories first, all of them shown, and a chosen main opens its subcategories as an indented list in a bordered group underneath it (on phones the sheet grows upward to fit). A chosen main means all of it; choosing subcategories narrows it, so the main shows as unselected while its group stays open, and choosing the main again widens it back to all. `kategori` in the URL lists mains and subcategories, e.g. `kategori=Samferdsel,Jernbane`. Adding a category is a line in the tree; renaming, merging or moving one also lists the old name in `retiredCategories`, and stored projects, suggestions (both read through the schema's JSON columns) and old links read as the new names at once.
- Project reference pages at `/prosjekt/[id]` with editable descriptions, project links, facts, a separate update timeline, and image credits. Updates come first and are the default section when there are any; a linked comment opens the discussion. Under the title sit the place, the developer and the project's site, then a timeline of its phases (Foreslått → Planlagt → Under bygging → Ferdig) across the panel, the end labels at the edges and the middle ones centred under their dots: the phases behind it quiet, the current one marked in its status colour, those ahead hollow. Each phase shows its optional start date (a year or a month), and “Ferdig” the year it's done or due; a Foreslått project has no such year. Under the intro, members see “Ser du noe som er feil eller mangler? Foreslå endring”, which opens the edit mode. The comments' sort sits on the tabs' line, with no count. Guests see a quiet, centred “Logg inn for å kommentere” line between the tabs and the comments, or under “Ingen kommentarer ennå”. On desktop a project slides out from the left edge as a sidebar covering the list, which stays mounted beneath it; the project's shape is selected and framed on the map while the others fade, and map clusters that would sit on it show their projects one by one. Its header holds the title, then a ⋯ menu (save, suggest a change or edit, copy link, and for moderators delete) and ✕. Closing it (✕, Escape or Back) slides it back out to the list, scroll position and map view included. On mobile projects open in a full-height drawer, with “Vis i kartet” to show them on the map.
- The list has two tabs, “Prosjekter” and “Nytt”, styled as the project page's tabs; “Nytt” gets a dot while any project in the place has news the user hasn't read. Projects show as compact rows by default, or as expanded cards with descriptions and photos (the layout is remembered in the browser), sorted by recent activity, newest or title. A row shows the place, the title, the status and its year, and the comment and update counts when there are any; it is a link to the project's page, so it opens in a new tab with a modifier key, while a plain press opens the project in the explorer. “Nytt” lists the same projects by what last happened on each, newest first. Each row names its project small on top (“Nytt prosjekt” for a new one), then what happened the way a comment reads in a thread, a symbol in the avatar's place and “name · when” on its first line, the time always relative: a speech bubble with the commenter and their words indented under it, a megaphone with the update's title and first paragraph, or a plus with the new project's name and description; a dot marks unread news. Comments within a week of the newest gather under one project, up to three, each opening the project at itself, then how many more. The count reads “Nytt fra N prosjekter”. A row opens the project at that update or comment. Its order is its own, so the sort and layout controls step aside. “Foreslå prosjekt” at the end of the list opens the new-project editor (suggestions for members, login for guests), starting where the map is.
- Statuses: Foreslått (grey, sparsely dotted on the map), Planlagt (dashed), Under bygging and Ferdigstilt. All four show by default. The layer menu's “Tegnforklaring” switch shows a legend of the statuses' colours and lines over the layer button; it starts off, and the choice is remembered in the browser. The list's collapse control has its own icon.
- One persistent discussion per project with replies, votes, and sorting by recent activity, newest, or top. Comments and replies can optionally reference any project update.
- A latest-update context card and a “since the latest update” filter that includes older conversations with recent replies. Updates never become comments or own separate comment sections.
- Existing comments, votes, and replies are preserved; previous update associations become optional references. Historical “Om prosjektet” entries are read as project context.
- HTTPS source links for project pages and updates; moderators can edit the reference description without publishing a timeline entry. Visible pages refresh every minute and when returning to the tab.
- Read state: for signed-in users, opening a project remembers it and how far they have read it. From then on, a card in the project list shows a quiet accent dot and count ("• 2 nye") when it has comments by others or updates since the user last opened it; the tooltip says what ("2 nye kommentarer · 1 svar til deg"). A card with news opens the project at the oldest unread comment or update, and opening a project from anywhere marks it read. Elsewhere, only the “Nytt” tab's dot says there is news.
- Saving ("Lagre"): signed-in users save projects from the project's ⋯ menu or an expanded card, with undo. The only effect is the "Lagret" page (in the account menu), which shows saved projects as the same cards as the project list, news included, with news first and then by latest activity (or alphabetically).
- A privacy page at `/personvern`, linked from login.
- Moderator tools: add project details, draw an area or alignment, undo points, enter coordinates, and publish project updates or status changes. On desktop a project is drawn on the explorer's own map area beside the panel, its tools (area or route, which end to extend, undo, clear, and the point count) in a small bar floating over the map's top; on phones on a map in the form, tools above it, which can take the whole screen. The new-project editor asks for name, category, the drawing, place and timeline first, then the optional details; until a place is picked, the drawing names it.
- New roads and railways (moderators): a switch under "Kartlag" in the layer menu draws railways and through roads (motorway to tertiary, not ramps or streets) under construction (solid) and proposed (dotted) from OpenStreetMap as candidates for new projects, railways pink and roads light red; a dot on the layer button shows it's on, and on desktop the list steps aside, its toggle hidden, until the mode is off. OSM's many ways per line become one candidate per line: ways join along shared nodes, a network splits between its sizeable named lines, parallel tracks and carriageways and pieces of one line across small gaps join again, and bridge, tunnel and station names don't count as line names. Each candidate gets one end-to-end alignment, and is drawn with its ways stitched together and parallel tracks once, so dotted lines keep an even rhythm. A bar over the map chooses railways and/or roads and under construction and/or proposed, and steps with `j`/`k` (or ‹ ›) through what no project covers yet, longest first, framing each; its X turns the mode off, and its ⋯ menu shows or resets hidden candidates, hides existing projects, and reads OSM again. The selected candidate's card names an overlapping project of its kind; "Opprett prosjekt" opens the new-project editor filled in from OSM (title from `description`, `name` or road number, status, category, developer from `operator` or the linked project site, year from `opening_date`, link from `website` or `wikipedia`, place, and the alignment); "Skjul" hides it for every moderator, with undo. OSM is only read when a moderator asks. The mode is remembered in the browser.
- Suggestions from signed-in members: a new project (the same editor, with details, drawing and photos), a correction (the project's edit mode; changed fields plus an optional note), or a tip (text, a required HTTPS source and an optional photo). Members follow their pending, approved and rejected suggestions at `/forslag`, under “Mine forslag” in the account menu and linked from their profile; reviews they haven't seen show as a badge on their account entry and a dot on their avatar.
- Moderation queue at `/forslag`, with a pending count in the moderator navigation. Each suggestion is one compact row (kind icon, project, then "N endringer", the category or the tip's first line, and the date); one row opens at a time, animating in place, and `j`/`k` or the arrow keys move between rows. Opened, a correction shows each changed field under its name: long text in full as a unified diff with a + / − gutter and added and removed words marked, short fields as old → new chips, and drawings as an old/new overlay with a point count and how far the centre moved. Fields changed since the suggestion was sent are flagged, and each field's ⋯ menu can leave it out of the approval ("Ikke ta med denne endringen", undone with "Ta med igjen"). The suggester's note is quoted under the changes. Approve (✓) and reject (✕, with an optional reason) sit at the bottom of the opened row; new projects and tips can be edited before approval, and tips get a headline. Moderators' own edits stay direct.
- Credits: approved suggestions credit their member quietly, as "via @username" in an update's date line and at the end of a project's facts, linked to their profile. Photo credits (`@username`) stay as before. Credits are read from approved suggestions (`app/lib/server/credits.ts`), never stored on the project, so renamed or deleted accounts follow.
- Responsive layouts, native modal focus management, keyboard dismissal, a search shortcut, and reduced-motion styling.

## Accounts and persistence

- One Google button for sign-up and login, followed by one-time username selection for new users.
- Unique public usernames with immediate availability feedback, Norwegian characters, and database-enforced uniqueness.
- Persistent sessions, optional profile bio/location, sign-out on other devices, and account deletion with recent authentication.
- The account menu (the avatar) holds the profile and its settings, Lagret, “Mine forslag” (members) or the queue (moderators), and a dark-mode switch; signed out, the page follows the system's light or dark setting.
- Comments use the verified account identity; votes, saved projects and read state persist across devices.
- Suggestions are stored in the `suggestion` table (migrations `0005_suggestions` and `0006_suggestion_seen`) and authorized on the server: members submit, only moderators review, and each suggestion is applied once. Members may send 10 suggestions an hour with at most 20 pending, and upload 30 photos an hour.
- Moderator access is configured with verified emails in `MODERATOR_EMAILS` and enforced on the server.
- Moderators and members upload project and update photos; browsers downscale them to 2000px before upload and they are stored in the database (`upload` table) and served from `/api/uploads/[id]`. Members' photos are served only to them and to moderators until a suggestion using them is approved. Projects without a photo show a category placeholder. The bundled `/images/*.jpg` photos are only used by example (seed/sample) projects.
- Local SQLite for development, with hosted Turso support using `DATABASE_URL` and `DATABASE_AUTH_TOKEN`.

`bun run setup` generates a local session secret, applies the committed Drizzle migrations, and seeds illustrative projects/comments. `bun run db:migrate` only applies migrations; `bun run db:seed` adds the illustrative content idempotently and refuses to run against a hosted database, so production starts empty. `bun run db:sample` adds fictional sample projects (areas, alignments, photos, updates and threaded comments) for local development; pass `--worktrees` to write them to every worktree's `local.db`. Use `bun run db:generate` after schema changes.

The seeded development projects use illustrative statuses, dates, descriptions, and approximate geometries. They are not an authoritative live development register. Seed profiles are explicitly marked as examples and their usernames cannot be claimed. Old localStorage demo activity remains in the browser and is not imported into real accounts.

Map tiles load from Esri's Light Gray Canvas service, with an OpenStreetMap street layer for detailed inspection and drawing. The services are credited on the map. Tile errors leave the project list usable. For smooth panning nothing moving on the map carries a CSS filter or container opacity (each would be recomposited every frame); tiles load once a zoom settles, and the explorer re-renders only when the set of projects in view changes. Google Geist fonts are loaded through `next/font`.

## Structure

- `app/components/explorer.tsx`: navigation, filters, project results, and account entry points, including the saved view; `project-card.tsx`, `panel-resizer.tsx` and `toast.tsx` render its list, list divider and confirmations (`toast.tsx` is the API; its UI, `toast-view.tsx`, loads apart); `app/lib/explore-state.ts` reads and writes its query string.
- Read state: `app/lib/server/unread.ts` counts unread activity on every project the user has opened, from each view's `seen_at` (`unreadActivity` lists the unread items themselves, for a later e-mail digest); `GET /api/seen` reads the counts and `POST /api/seen` records one project as opened and read. `app/lib/unread.ts` holds the shared types and summary text; `unread-provider.tsx` keeps the counts in sync with the community data; `saved-projects.tsx` is the self-contained saved list, built from `project-card.tsx`.
- `app/components/project-map.tsx`: Leaflet map, project overlays, and geometry drawing.
- `app/components/project-post.tsx`: project reference page and update timeline.
- `app/components/project-discussion.tsx` and `app/lib/discussion.ts`: shared project discussion, optional references, and activity-aware filtering.
- `app/components/project-editor.tsx`: project creation workflow, also used for suggested projects.
- `app/components/suggestion-list.tsx`, `app/lib/suggestions.ts` and `app/lib/server/suggestions.ts`: the `/forslag` page, suggestion rules, and the moderation queue's server side. Request schemas (`app/lib/suggestion-schemas.ts`, `app/lib/account-schemas.ts`) are server-only, so the page ships no zod.
- New roads and railways: `app/lib/osm-build.ts` turns Overpass ways into candidates (pure, tested in `tests/osm-candidates.spec.ts`); `app/lib/osm-candidates.ts` holds their types, titles, project drafts and matching against projects; `app/lib/server/osm-candidates.ts` reads Overpass on request only (falling back across public servers; `OSM_OVERPASS_URL` puts another first), keeps the result in `external_cache`, and keeps hidden candidates in `osm_dismissal` (migration `0008_osm_candidates`); `GET`/`POST /api/osm-candidates` is moderator-only; `app/components/osm-review.tsx` holds the review state and `osm-panel.tsx` the bar and card, loaded only while the mode is on.
- `app/lib/diff.ts`: paragraph and word diffs, and geometry change summaries and overlays, for reviewing suggestions (tested in `tests/diff.spec.ts`). The diff colours are `--color-diff-*` tokens in `app/globals.css`.
- `app/lib/data.ts`: data types, shared project helpers (place, links, statuses), and illustrative project content.
- `app/lib/auth-config.ts`: Google OAuth, database sessions, and account configuration.
- `app/lib/db/` and `drizzle/`: database schema, connection, and migrations.
- `app/api/` and `app/lib/server/`: account, public-profile, and community APIs with server-side authorization; each community mutation is a function in `app/lib/server/community.ts`.
- `app/components/auth-provider.tsx` and `community-provider.tsx`: session state (root layout) and shared project data (explorer layout only).
- `tests/`: isolated database integration and browser tests.
- `app/globals.css`: design tokens (colours, type, shadows, breakpoints, animations) and base styles. Components style themselves with Tailwind; `*.module.css` next to a component holds CSS that needs selectors (`project-post`, `project-discussion`), and `project-map.css` overrides Leaflet's own markup.

## Discussion storage compatibility

All comments belong to `projectId`. `updateId` is optional in the API and is only a reference, never a separate discussion boundary. An empty string in the existing database column represents no reference; reads normalize old overview references and missing update references to an omitted `updateId`. This preserves existing rows and votes without rebuilding tables. Replies must stay within the same project but can cite a different update.

Run `bun run db:migrate` for existing installations. Migration `0011_category_merge` rewrites stored categories to three mains: Energi and Vann og avløp become Annen infrastruktur, Offentlige bygg part of Byutvikling; subcategories keep their names. Migration `0009_saved_projects` renames `following` to `saved`: the `bookmark` table (exported as `projectView`) now holds every project a user has opened, and earlier follows become saved projects. Migration `0004_project_follows` keeps the `bookmark` table so existing saved projects become followed projects, and adds `following` (false after an explicit unfollow), `created_at` and `seen_at`, the last two set to the migration time so nothing old shows as unread. Migration `0007_category_tree` turns each project's `category` into a `categories` list (Bolig, Næring and Byrom og park become subcategories of Byutvikling), converts stored suggestions the same way, and gives the example projects subcategories. Migration `0002_infrastructure_categories` moves the government quarter to Offentlige bygg, and the development seed adds national infrastructure examples (Follobanen, Fornebubanen, E39 Rogfast, Sotrasambandet, Hålogalandsbrua, Ny vannforsyning Oslo, Nye Aker sykehus, Northern Lights). Migration `0001_project_sources` adds verified project links and sample-data labels to the seeded projects without replacing their content or existing links. The links lead to project owners, municipalities, or project designers; the illustrative statuses and updates are still not a live register.
